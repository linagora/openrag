---
title: Catalog and vector reconciliation
---

Postgres and Milvus can disagree after interrupted indexing, deletion or restores. Retrieval checks catalog membership before returning chunks and fails closed if that check fails. Results may contain fewer matches than requested. The counter `openrag_retrieval_orphan_chunks_dropped_total` counts drop occurrences, so repeated retrievals can count the same chunk again. To help identify affected documents, warnings sample up to ten distinct partition/file keys, truncated to 128 characters per value. Warnings are limited to once per minute per process; catalog checks and the counter still run on every call.

Run `uv run python scripts/reconcile_catalog.py --partition NAME` with the deployment's usual configuration. The default is read-only, uses pages of 500 rows and excludes indexing timestamps younger than one hour. Adjust `--page-size` (maximum 1000) and `--grace-seconds` to suit the workload. Choose a grace window longer than normal indexing jobs. Each output line is JSON; findings stream as the scan progresses, followed by a summary. Exit codes are 0 for no findings, 1 for findings (including repaired ones), and 2 for failure. Unverified catalog timestamps are informational and do not change the exit code. A failed or interrupted run is incomplete; rerun it before drawing conclusions.

To remove aged orphan chunks, first pause new indexing, copy, replace and delete operations and drain in-flight work, then add `--repair`. Keep writers paused until it finishes. Repair rechecks catalog membership and deletes only the reported chunk IDs. The recheck and deletion are not atomic across stores, so the grace window alone cannot make live repair safe. Run the read-only check again afterward. Catalog rows are never removed.

Missing chunks require an operator to decide whether to re-index or remove the catalog entry; empty documents may legitimately have no chunks. Unknown or invalid chunk timestamps are reported without repair. Timestamp differences are report-only and split in two. An indexing timestamp mismatch lists chunks of a file that also has chunks matching its catalog timestamp, which usually means a replacement left its previous chunks behind. An unverified catalog timestamp lists files where no chunk matches the catalog timestamp, so the catalog value itself is unreliable: the migration that added `files.indexed_at` set every existing file to the migration time, and copies made by earlier releases kept the source's chunk timestamps. A re-index that produced no chunks and also failed to remove the previous ones falls into this second category. Matching timestamps do not prove a complete or unique chunk set: the summary explicitly marks duplicate-set verification as unsupported. Reliable duplicate repair needs a durable indexing-generation identity.

Online reports are observations, not a snapshot across both stores. For a completeness check after a restore or bulk import, finish the writes, wait out the grace window and scan each affected partition, including deleted partition names when looking for their orphan chunks. The `all` wildcard is rejected: each run must name one concrete partition. Grace values must be finite, nonnegative and produce a cutoff within Python's supported datetime range.

New copies use a fresh indexing timestamp shared by both stores, so they receive the same grace period as newly indexed documents. Older copies are reported as unverified catalog timestamps.

## Uploaded files no catalog row uses

Deleting a file used to leave its upload under `DATA_DIR`, and with `FILE_FENCES=ray` it still does. To list the uploads no catalog row references, run `uv run python scripts/find_orphan_originals.py` where the API runs, with its configuration: the catalog stores each upload's path as the API sees it. In the API container, run `uv run --no-dev python /app/scripts/find_orphan_originals.py` from its working directory, since a relative `DATA_DIR` resolves against it. Only uploads are considered, that is files directly under `DATA_DIR` whose name starts with the upload's timestamp prefix, together with their `SAVE_MARKDOWN` copies. Files younger than 24 hours are skipped, since an upload is on disk before its job writes its row: set `--min-age-hours` (at least 1) above your longest queue wait. Each output line is JSON, one per unreferenced file, followed by a summary. Exit codes are 0 for none, 1 for some (deleted ones included) and 2 for failure.

Add `--delete` to remove them. It deletes exactly the files listed, each checked against the catalog again just before it goes, so a file a copy in another partition still uses is kept. It deletes nothing and fails instead in two cases. One is when no upload under `DATA_DIR` is referenced at all: the script is most likely running with another `DATA_DIR` or database than the API. The other is while an indexing job created before the cutoff hasn't finished, since its upload has no catalog row yet: run it again once the job settles.
